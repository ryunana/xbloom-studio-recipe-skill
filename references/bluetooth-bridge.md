# 电脑蓝牙冲煮

配方生成不需要读这份文档，也不需要任何蓝牙。本文只处理"能不能让电脑替机器冲一杯"。

## 先说结论：为什么传输层自己写

1.1.0 版本试过接一个现成的第三方桥接程序，省事，但它在真机上会**报成功而实际没冲**：
机器沿用了上一次的研磨档位，出来的粉粗细是错的。对一个卖点是"精确到档"的 skill，
这一条就够了，所以 1.3.0 改成自己实现。

下面是当时踩到的七个坑。每条都独立成立，跟具体实现无关——任何人写这一层都会碰到：

| # | 该怎么做 | 做错了会怎样 |
|---|---|---|
| 1 | 连上之后先发握手（`8100`） | 机器静默忽略后续所有命令，不报错 |
| 2 | 写入用 Write Without Response | 用 Write With Response，失败会被吞掉，调用方仍以为成功 |
| 3 | 必须发粉量帧（`8102`） | 固件拿不到剂量，配方不提交，研磨沿用上一次的档位 |
| 4 | 配方尾字节放**粉水比×10**，不是总水量 | 固件校验不过，同上，研磨不更新 |
| 5 | 杯型区间按实际滤杯下发（Omni 是 `110/90`） | 写死别的值机器虽然容忍，但没有任何依据 |
| 6 | 先切到 Pro 模式再发配置帧 | Auto 模式不接配置帧，全部无回执（本机实测确认） |
| 7 | 等机器自己的完成事件，不看接口返回值 | 接口返回 ok 和"机器冲完了"是两件事 |

第 3 + 4 条合起来就是那个坑：机器拒收配方后，**用上一杯的粗细磨这一杯**。

## 本 skill 现在提供什么

**协议层** `scripts/xbloom_proto.py`：纯标准库，离线可验证。

- 构造帧（CRC16 多项式 `0x8408`、初值 0、小端、类型 1/2）
- 编码配方 blob（含浮点闸门对齐、127 ml 拆块、pattern/温度/流速编码）
- 解码机器回复（ACK / 周期上报、24 位拒绝码按位解释）
- 生成完整的冲泡帧序列（握手 → 回主屏 → 粉量 → 杯型 → 配方 → 执行）
- **自带实测对拍**：`python3 scripts/xbloom_proto.py` 会拿 5 条真实报文逐字节比对

**传输层** `scripts/xbloom_brew.py`：bleak 驱动，真连机器。

- 握手 → 回主屏 → 粉量 → 杯型 → 配方 →（可选）执行
- 每条命令都等机器回码；拒绝码立刻按位解释
- 等 `40512` 才算冲完；`40511` 停止、`40522` 缺水、`8203/8204` 异常都单独报
- 写入统一用 Write Without Response
- 发生超时不重传

一条命令入口：`bash scripts/brew.sh [子命令]`（自动挑一个装了 `bleak` 的 python；装法见 README 的「运行前提」）。

## 三条路径，按风险从低到高（三条都已实现）

### A. 只用配方（默认，无蓝牙）

生成配方 → 人手动打进 App。零风险，也是绝大多数场景。

### B. Load-only：把配方装进机器，不启动

```bash
bash scripts/brew.sh brew --recipe recipes/current.json --load
```

握手、粉量、杯型、配方全部发完，**停在执行帧之前**。机器收到配方但不会出水。

### C. 远程启动

```bash
bash scripts/brew.sh brew --recipe recipes/current.json --start
```

在 B 的基础上，倒数 3 秒后发执行帧，并持续听完成事件。**这一步会真的出热水**，前提是杯子、滤纸、水、豆都已就位。

## 传输层

本包自带一层（`xbloom_brew.py`），只依赖 `bleak`。如果想用更成熟的第三方实现：
也有实现把 load 与 start 分得更彻底：装载后由**机器屏幕上的人**按键确认。不想让 agent 有机会启动咖啡的话，那种做法更稳。

## 闭环判定：怎么才敢说"冲完了"

依次满足，缺一不可：

1. **每条命令都有 ACK**：回复帧的命令码等于刚发出去的命令码
2. **拒绝码为 0**：否则按位解释原因，不要重发
3. **收到 `40512`（RD_ENJOY）**：机器自己说冲完了
4. **分段序号 `40510` 序列连续**：证明每一段真的注水了，而不是跳段
5. **水量/秤重曲线合理**：`40523` 与 `10507` 的末值，与配方总水量对照（注意密度与 15–19 g 秤偏移，见设备事实第 6 节）

任何一步缺失，只能说"机器接受了请求"，不能说"冲完了"。HTTP 200、`brewActive: false`、桥接 dashboard 变绿，都不是完成证据。

## 真机验收：五级，逐级放行

| 级别 | 动作 | 通过标准 | 需要豆/水 |
|---|---|---|---|
| 0 | `python3 scripts/xbloom_proto.py` | 5 条实测报文全对 | 否 |
| 1 | `bash scripts/brew.sh scan` | 列表里出现 `XBLOOM …` | 否 |
| 2 | `bash scripts/brew.sh grind --size 50` | 磨盘真的转，屏幕研磨度是 50 | 否（空仓） |
| 3 | `bash scripts/brew.sh brew --recipe recipes/current.json --load` | 机器收到配方、不出水 | 否 |
| 4 | `bash scripts/brew.sh brew --recipe recipes/current.json --start` | 出杯，且收到 `40512` | 是 |

**级别 2 是最便宜的一枪**：空豆仓、无水、无杯，一个动作同时验证帧结构、Write-Without-Response、机器是否真的收包。级别 2 不通过，别往下走。

**权限前置**：macOS 在没有蓝牙授权时会直接杀进程（不是报错）。`brew.sh` 会先探测并给出修法；在自己的终端里运行最省事。

## 安全边界

- 显示配方与指纹，再谈冲煮；改动过的配方要重新确认
- 装载（load）与实际启动（start）永远分两步；默认只做 load
- 任何超时或断连：先看机器，**不要重发**。上游类实现对写入失败不报错，重发等于赌第二次不会重复启动
- 桥接监控页面（Dashboard）里的操作与本 skill 可能互相抢机器；同一时间只允许一个操作者
- 本文档描述的能力已在本机（Studio / `V12.0D.400`）通过第 4 级验收，但那是一台机器、一支豆、一次出杯。
  换机器、换固件、换豆子，请从第 2 级重新走一遍，不要直接拿别人的"成功了"当自己的依据
