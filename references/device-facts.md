# xBloom Studio 设备事实（带出处）

这份文档只放**会影响配方结果或会导致"看起来连上了但没冲"**的机器事实。每条都标了来源等级：

- **【通信】** 从真实通信记录逐字节核对，可信度最高
- **【行为】** 从机器的实际反应确认（做什么、不做什么）
- **【实测】** 拿真机量出来的数字（时间、重量、边界）
- **【单源】** 只有一处提到，尚未交叉确认

配方规则本身（研磨区间、archetype、翻车路线）仍在 `SKILL.md`，本文不改那些判断。

## 1. 连接与命令：三个会让整条链路静默失效的前提

| 事实 | 后果 | 来源 |
|---|---|---|
| 连接后必须先发握手 `8100`，载荷恒为 `[185, 1]` | 不发握手，机器在 BLE 层收下每一个字节但**完全不响应**：不亮屏、无提示音、无回复 | 【通信】 |
| 写特征值必须用 **Write Without Response** | 用 Write With Response 在 macOS 上直接被拒（`CBATTErrorDomain 14`），而很多实现会把写错误吞掉继续返回成功 | 【通信】 |
| 配置帧与配方帧（`8102` / `8104` / `8001`）只在 **Pro 模式**被接受 | 停在自动模式时全部无回执，机器不报错也不执行；切 Pro 之前还要先回主屏并退出配方界面 | 【实测】 |

## 2. 研磨档位：不需要任何偏移

- 线上发的是 **1–80 原值**（就是 App 上看到的数字），机器内部存 `size + 30`，回报时再减 30。**【行为】**
- 所以"发送端要不要 +30"是伪问题：**发送端不偏移，只有读机器回报时才减 30**。【行为】+【通信】（MachineInfo 字段 `raw − 30`）
- 关掉研磨：blob 的研磨字节写 `0`，并改用 `8004`（无研磨）而不是 `8001`。【行为】

## 3. 研磨提交闸门（最容易踩、后果最隐蔽）

机器只有在下面这个等式成立时，才会**提交整份配方（含研磨档位）**：

```
trunc( (ratio_byte / 10) × dose )  ==  Σ(每段线上水量)
```

- 不成立 → 机器**保留上一次的研磨档位**，用新的注水参数冲。这叫 **grind-size bug**：你以为改了研磨，实际磨的还是上一杯的粗细。**【行为】**
- `ratio_byte` = 配比 × 10（1:16 → 160）；它**不是**总水量，也不是 CRC。**【通信】+【行为】**
- `dose` 来自 `8102` 帧。**不发 8102，机器不知道粉量，闸门必然不过。**【行为】
- 推论：配方 JSON 里的 `粉量 × 配比` 必须等于分段水量之和，且都要和真正发出去的整数一致。我们自己的编码器已经按 float32 精度对齐（`scripts/xbloom_proto.py`）。

## 4. 温度有两个域，配方存的是"线上域"

| 域 | 取值范围 | 含义 |
|---|---|---|
| 线上（配方里存的就是这个） | `20` = RT，`40–95` 真实摄氏度，`98` = BP | 写进 blob 的字节 |
| 显示/旋钮（机器回报 `8108`） | J15 摄氏 `39–96`，华氏 `103–204` | 旋钮位置，不是存下来的值 |

- 对外表述统一成：**可设数值 40–95 °C**，另有 RT 与 BP 两个特殊档位（BP 存 98，但 98 不是可设温度）。`SKILL.md` 已按这个写，两处不要打架。**【行为】+【单源】**
- 配方设计仍建议落在 86–96 显示温度，不要用 RT/BP 做日常咖啡。

## 5. 每段参数的机器边界

| 参数 | 线上边界 | 说明 |
|---|---|---|
| 段水量 | 1–240 ml（App 上限） | **>127 ml 会被自动拆成多块**（127 + 余数），机器接受，实测 300 ml 单段可跑 |
| 流速 | 3.0–3.5 ml/s | 三处独立来源一致；**7.0 是协议字节装得下，不是机器支持** |
| 驻留 | 0–59 s | 编码为 `(-秒) & 0xFF` |
| 段数 | 1–9（App） | 本 skill 的设计约束是 3–5 段，比机器上限更严，属有意为之 |
| 注水模式 | 字节 `0`=中心，`1`=环绕，`2`=螺旋 | 语音播报确认。**API 整数是另一套（1/2/3），不能与字节互推** |
| 研磨转速 | 60–120，步进 10 | 只写进第一段的时序块，其余段为 0 |

## 6. 水量与秤：为什么"看着少"

- 93 °C 水的密度约 **0.9634 g/ml** → 目标 240 ml 在杯里约 **231 g**，不是 240 g。**【实测】**
- 机器内置秤在热液体下有一个 **约 15–19 g 的固定正偏移**（不随水量比例变化），所以**秤读数不能当作出水量**。**【实测】** 表：100 ml → 秤 85.1 g；400 ml → 356.4 g；800 ml → 729.8 g。
- 机器实际出水与预期偏差在 **2–3%** 内；拆成多段不改变总水量精度。**【实测】**
- 水箱容量：**>500 ml 的配方有中途断水风险**（报错码 `40522`），540 ml / 800 ml 均实测翻车。**仅适用于水箱模式**；接外接水管的机器没有这个上限。**【实测】**
- 机器信息帧里"水量是否足够"那一位，**在接外接水管的机器上恒为 0**（没有水箱浮子）。碰到它之前先看"水路来源"字节，否则会把正常机器误判成缺水。**【实测·本机】**
  实测样本：`水路由=1(外接)`、`水位位=0`、研磨回报 50、序列号 `J15A01C4…`（后三位隐去）、固件 `V12.0D.400`。

对配方的意思：**总水量超过 500 ml 时先在提示里要求中途加水**；杯里读数对不上目标时，先怀疑温度和秤偏移，不要立刻改研磨。

## 7. 命令被拒时，机器回的是自己的码（最难发现的一个坑）

- 一条命令被拒绝，机器的回复**和成功一模一样**（回它自己的命令码），区别只在回复里 3 字节大端错误码。
- 该错误码是**位域**：机器会把多个条件叠加起来，必须**按位读**，不能按值比对——按值比对会把 `0x400040` 这种组合读成"成功"。**【行为】**

| 位 | 含义 | 人话 |
|---|---|---|
| `0x000040` | no_water | 缺水 |
| `0x000800` / `0x001000` | not_on_home_screen | 不在主屏，先回待机界面 |
| `0x100000` | not_ready | 断电后遗留锁存，机器拒绝除握手外的一切命令 |
| `0x200000` | restore_incomplete | 同上，第二个锁存 |
| `0x400000` | recipe_rejected | 配方被拒：检查水量与分段 |
| `0x000100`…`0x800000`（9 个） | machine_busy | 忙 / 当前不接受该命令 |

**遇到 `0x100000` / `0x200000` 时，重试无用**：机器看起来"连上了但什么都不做"，实际是断电后的锁存。做法是**整机重新上电**，不要重发命令，更不要怀疑蓝牙。**【行为】+【实测】**（有记录：连续三杯每条命令都被 `0x100000` 拒绝，什么都没磨）

## 8. 杯型区间 `(theMax, theMin)` 不是我们能算的

- 这两个值（`theMax` / `theMin`）随配方一起由服务端下发，**本地推不出来**，不要试图自己算。
- 已确认的值：**Omni dripper `(110, 90)`、Other `(200, 80)`**；xPod / Tea 只有默认值 `(200, 80)`。**【通信】+【单源】**
- 这两个数的实际语义仍未确定，机器在取值不同时也照常冲。所以：**不要自己发明数值**（比如 `90/40`），按杯型用上表；它出问题时优先怀疑别的。

## 9. 停止比暂停可靠

- `4507` 停止：实测确认，回复明确。
- `8019` 暂停、`8024` 之类恢复类命令：只有单源记录，未在机器行为中交叉确认。**【单源】**
- 所以真机第一枪先测**停止**，不要先测暂停；暂停/恢复不可靠时，用机器上的物理键。

## 10. 实践中定下来的几条做法

- **不要把 8006（进入研磨页）塞进配方流程**：会打乱机器状态。手动磨豆才用 `8006 → 3500 → 3505`。**【行为】**
- **load 与 start 必须分开**：把"把配方装进机器"和"真正开始"拆成两步，装载后机器会**在屏幕上等人确认**。这是唯一不依赖提示词的安全闸门。**【实现共识】**
- **保持长连接**可以跳过每杯重新连接 + 握手，但断开后必须重新握手，否则静默失效。**【通信】+【实现共识】**

## 11. 本机实测确认/推翻清单（2026-10-27，Studio / V12.0D.400）

这一节全部来自本机真机操作，**推翻过公开资料的若干说法**，优先级高于前面各节。

| 结论 | 证据 |
|---|---|
| **配方帧必须用 Type 1**（`58 01 01` + 原始字节） | Type 2（`58 01 02`）发 8001/8004 机器**完全没有反应**，连拒绝都不给；改 Type 1 后立即回执，与官方 App 发出的格式一致 |
| **Auto 模式不接配置帧** | Auto 下 `8104`、`8001/8004` 无回执；切 Pro（11511 `00000000`）后 `8102/8104/8001` 全部回执 |
| **切模式前必须先回主屏 + 退出配方界面** | 只发 11511 切不动；补 `8022` + `8017` 后才生效（实测模式确实从 Pro 变回 Auto） |
| **机器信息 40521 只在握手时上报一次** | 要读最新状态得再握一次手（官方 App 同做法） |
| **ACK 里没有错误码** | 所有回执都是 12 字节、无 payload、状态位 `C1`；把第 12-14 字节当错误码会误读序列号/秤重 |
| **40506 = 研磨过程事件** | 手动研磨期间出现，公开资料未记录 |
| **40511 停止回执先于 40512 完成事件约 2 秒** | 实冲一杯：4 段注水 → 40511 → 40512。把 40511 当终态会误报失败 |
| **40512 完成事件本身会丢** | 2026-10-28 实冲：4 段注水事件全部收到、收到 40511，之后 8 秒内没有 40512。水确实出完（192.7 s，与配方一致）。结论：**以「每段都收到注水事件」为主判据**，40512 只作加分 |
| 本机身份 | 型号 Studio；序列号 `J15A01C4…`（后三位隐去）；固件 `V12.0D.400`；外接水路线；MTU 247 |

**已验证可用的冲泡序列**（每一步都拿到回执，未启动时不出水）：

```
8100 握手(会重试) → 8022 回主屏 → 11511 切 Pro
→ 8102 粉量 → 8104 杯型 → 8001 配方 → [8002 执行]
```

手动研磨（已验证，磨盘确实转动、屏幕显示档位）：`8022 → 8006 → 3500 → 3505`。
